GitHub Copilot i team SAS

En kort guide til hvordan vi bruker kodeagenter i teamet: hva begrepene betyr, hvordan bitene henger sammen og hva du må stille inn.

Skrevet for teammedlemmer, ikke for agenter. Dette er en guide for oss mennesker. Agentene får sine instruksjoner fra AGENTS.md, CODING_STANDARDS.md og .github/skills/, og denne siden er bevisst ikke lenket derfra. Detaljene står i dokumentasjonen vi lenker til. Status per november 2026.

Kort fortalt

  • Vi bruker Copilot CLI i terminalen, alltid inne i sandkassen cplt. Start med cplt direkte. nav-pilot er valgfritt og gir bare Navs felles skills, agenter og hooks i tillegg.
  • Vi starter alltid fra helse-sas-meta. Da får agenten med seg ordlisten, ADR-ene, kodestandardene og skillene våre.
  • Større arbeid går slik: grill → spec → tickets → implement → retro. Specer og tickets er issues i navikt/sas-issues.
  • Testene skal kjøre i sandkassen uten allow_docker. Postgres og Kafka kjører utenfor, og testene kobler seg til via miljøvariabler.
  • På Nav-utstyr er sandkasse påkrevd. Copilot-appen går ikke gjennom cplt, så bruk den til oversikt, ikke til agentarbeid i repoene.
  • Copilot på github.com er en annen harness. Den kjører i GitHubs sky uten sas-meta-konteksten vår, så gi den bare små oppgaver i ett repo og PR-gjennomganger.

Vår harness

Harnessen vår består av fem deler:

  • Copilot CLI: agentløkka og verktøyene.
  • cplt: sandkassen.
  • nav-pilot (valgfritt): legger til Navs skills, agenter og hooks.
  • helse-sas-meta: AGENTS.md, CODING_STANDARDS.md, GLOSSARY.md, ADR-er og skillene våre.
  • navikt/sas-issues: specene og ticketene.

Modellen er den delen vi bytter oftest. Resten er det som gjør at agenten jobber på vår måte.

Flyten: fra idé til kode

/grill-with-docs → /to-spec → /to-tickets → /implement <nr> → /code-review → /retro
StegHva skjerResultat
/grill-with-docsAgenten stiller spørsmål om planen i runder, med anbefalte svar, til dere har en felles forståelse. Den starter med tverrfaglig-oppstart (hvem er med?) og avslutter med after-grilling (varsler og melding om vedtak). Gjør dette gjerne i fellesskap med fag, design og juss. /grill-me er den lette varianten uten dokumentasjon.Oppdatert GLOSSARY.md og nye ADR-er

Fasene i en epic omtaler vi med både nummer og navn, for eksempel «fase 2 (Verifisering)». Oversikten over issues ligger i sas-issues.

Modeller

Bytt modell med /model midt i en økt. Modellene koster forskjellig: hver forespørsel trekkes fra premium-kvoten med en egen multiplikator. Se GitHubs modelloversikt. Dette er utgangspunktet vårt, ikke en regel:

OppgaveModellHvorfor
Grilling, spec, arkitektur og reviewClaude OpusResonnerer best og ser konsekvenser
/implement og vanlig kodearbeidStandardmodellen i nav-pilot (GPT-6.1 Sol) eller Claude SonnetGod balanse mellom kvalitet, fart og pris
Sub-agenter, oppslag og små endringerEn rask modell (Haiku, Flash)Billig og rask nok

Kom i gang

brew install navikt/tap/cplt
cd ~/git/nav/helse-sas-meta
cplt doctor               # sjekker oppsettet
cplt                      # starter Copilot CLI i sandkassen
cplt -- --model claude-opus-5.5   # alt etter -- går rett til copilot

Vil du også ha Navs felles skills, agenter og hooks, installer navikt/tap/nav-pilot og start med nav-pilot i stedet. Den starter den samme cplt-en for deg. Skillene våre i sas-meta får du uansett. Med cplt --shell-install kjører også en vanlig copilot i sandkassen.

  • Start fra helse-sas-meta, ikke fra app-repoet. Konteksten følger mappen du står i. Starter du i spleis/, mister agenten ordlisten, ADR-ene og skillene våre.
  • Første gang i et repo med .cplt.toml må du godkjenne policyen med cplt trust.
  • Installasjon og oppsett er beskrevet i README for nav-pilot og README for cplt.

Innstillinger i sandkassen

Kjør kommandoene utenfor sandkassen, i en vanlig terminal. De gjelder fra neste gang du starter cplt. Uten --local lagres innstillingen i din globale cplt-konfigurasjon. Med --local gjelder den bare denne checkouten. Se gjeldende oppsett med cplt config show eller cplt settings, og få forklart en nøkkel med cplt config explain <nøkkel>.

Tester med Postgres og Kafka, uten allow_docker

allow_docker gir agenten tilgang til Docker-socketen, og det er i praksis root på maskinen. Vi bruker heller TestDatabase fra postgres og TestKafka fra kafka-test i sykepenger-libs (står i CODING_STANDARDS.md). Er miljøvariablene satt, kobler testene seg til serverne der. Er de ikke satt, starter testene egne testcontainere, som før.

# 1. Start containerne utenfor sandkassen
docker run -d --rm --name test-postgres -e POSTGRES_PASSWORD=test -p 5432:5432 postgres:18-alpine
docker run -d --rm --name test-kafka -p 9092:9092 apache/kafka-native:3.9.1

# 2. Eksporter variablene i skallet du starter cplt fra (f.eks. i ~/.zshrc)
export TEST_POSTGRES_JDBC_URL='jdbc:postgresql://localhost:5432/postgres?user=postgres&password=test'
export TEST_KAFKA_BOOTSTRAP_SERVERS=localhost:9092

# 3. Én gang: slipp variablene og portene inn i sandkassen
cplt config set sandbox.pass_env TEST_POSTGRES_JDBC_URL
cplt config set sandbox.pass_env TEST_KAFKA_BOOTSTRAP_SERVERS
cplt config set allow.localhost 5432
cplt config set allow.localhost 9092

Repoer som fortsatt bruker egne testcontainere, bytter vi over når vi likevel endrer dem. Se README-ene for libs/postgres og libs/kafka-test, og cplt: Docker og Testcontainers.

Tips: lag et alias

Du slipper å huske flaggene hvis du lager en funksjon i ~/.zshrc. Den kan starte Postgres og Kafka hvis de ikke kjører, sende miljøvariablene rett inn med --pass-env, åpne portene for denne økta og velge modell. Da trenger du ikke stegene 2 og 3 over.

sas() {
  docker ps -q -f name='^test-postgres$' | grep -q . ||
    docker run -d --rm --name test-postgres -e POSTGRES_PASSWORD=test -p 5432:5432 postgres:18-alpine
  docker ps -q -f name='^test-kafka$' | grep -q . ||
    docker run -d --rm --name test-kafka -p 9092:9092 apache/kafka-native:3.9.1

  cd ~/git/nav/helse-sas-meta &&
  TEST_POSTGRES_JDBC_URL='jdbc:postgresql://localhost:5432/postgres?user=postgres&password=test' \
  TEST_KAFKA_BOOTSTRAP_SERVERS=localhost:9092 \
  cplt --pass-env TEST_POSTGRES_JDBC_URL --pass-env TEST_KAFKA_BOOTSTRAP_SERVERS \
       --allow-localhost 5432 --allow-localhost 9092 \
       -- "$@"
}

alias opus='sas --model claude-opus-5.5'    # grilling og spec
alias sonnet='sas --model claude-sonnet-5.5'

Alt etter -- går til copilot, så opus starter med Opus, og sas -p "kjør testene i spleis" kjører én prompt uten interaktiv økt. Se modell-ID-ene med /model i en økt.

Copilot-appen eller CLI?

Copilot-appen er fin til å følge med på issues, PR-er og økter, og til agenter som kjører i GitHubs sky. Kjører den agenten lokalt på maskinen din, mister du dette sammenlignet med CLI i cplt:

  • Ingen cplt. Appen har sin egen lokale sandkasse, men ikke Navs policy, der kjernen stopper tilgangen til nøkler, tokens og .env-filer.
  • Ingen git- og gh-vakt. cplt stopper push til main, force-push, merging og releaser.
  • Ingen .cplt.toml per repo og ingen innstillinger fra denne siden. Appens sandkasse stilles inn for seg.
  • Ingen nav-pilot. Du mister hooks, oppstartsoppsett og OTEL-sporing.

På Nav-utstyr er sandkasse påkrevd (ki-utvikling.nav.no). Slik vi forstår det i november 2026, er cplt den enkleste måten å oppfylle kravet på. Gjør derfor agentarbeid i repoene med cplt, direkte eller via nav-pilot. Se også GitHub om lokale sandkasser.

Copilot på github.com

Du kan også bruke Copilot rett på GitHub: fra github.com/copilot, fra fanen Agents i et repo, ved å tildele et issue til Copilot, eller ved å be Copilot gjennomgå en PR. Da kjører agenten i GitHubs sky, enten i en skysandkasse eller på en GitHub Actions-runner. Det er en annen harness: samme slags agentløkke, men et annet miljø, en annen sandkasse og en annen kontekst.

Den største begrensningen for oss er konteksten. Flyten vår, med ordlisten, ADR-ene, specene i sas-issues og skillene, bor i sas-meta. En agent på github.com som jobber i spleis, ser ingenting av det med mindre du lenker til ticketen og ber den lese den. Gi den derfor en ticket som står på egne ben. Tips til prompting

  1. Gi kontekst og «hvorfor» når du starter grillingen. Eksempel: «/grill-with-docs Vi vil ha en ny abstraksjon, sp-sykepengegrunnlag. Den skal ligge etter AvventerVilkårsprøving … Input fra Spleis i behovet er …»
  2. Svar kort på spørsmålsrundene. Skriv «q1 ja, q2 ja, q5 nei, egen tilstand». Legg til «obs! …» for det agenten ikke har spurt om.
  3. Bruk én ny økt per ticket. Skriv /implement 304. Justeringer kan stå i samme prompt: «/implement 305. Vi vil at ID-en i behovet er søknadMeldingsreferanseId, så oppdater specen også.»
  4. Be om oppfølgingstickets underveis. Eksempel: «… og lag en ticket på å fjerne togglen senere i fase 1».
  5. Kjør /retro etter hver implementering. Det er slik harnessen blir bedre.
  6. Still små spørsmål om domenet og koden. Eksempler: «hva skjer i Spleis hvis arbeidsgiveren er en person?» eller «bruk /observability-debugging: hvorfor feiler sparkel-x i prod?». Alle repoene er sjekket ut under sas-meta, så agenten finner svaret selv.
  7. Spør om ADR eller standard før du ber om endringer. «Er dette en ADR eller CODING_STANDARDS?» gir bedre resultat enn å be agenten skrive med en gang.
  8. Når sandkassen stopper noe, ikke be agenten om å gå rundt det. Fiks innstillingen utenfor sandkassen og start på nytt.
